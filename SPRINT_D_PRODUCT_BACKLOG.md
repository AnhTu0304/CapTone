## 1. Chiến lược Triển khai theo Thứ tự Dependency (Phase 0 → Phase 7)

Không triển khai đồng thời mọi workstream. Thứ tự bắt buộc:

1. **Phase 0 — Repository & Environment Assessment (`DONE trong MODE 1`):** Audit codebase, CSDL test, CI/CD, OWASP & lập Backlog (`3 SP` đã thực hiện kiểm toán).
2. **Phase 1 — Database Governance (`SD-01` — P0 CRITICAL):** Hoàn thiện `migrate.ts`, `schema_migrations`, advisory lock, `--baseline`, tách seed khỏi `00_init_full_database.sql`, sửa `cd.yml` / `ci.yml` backup gate & compose check. *(Không cho phép chạy bất kỳ migration mới nào ở runtime trước Phase 1).*
3. **Phase 2 — TLS & Runtime Security (`SD-02` — P0 CRITICAL):** Cấu hình Nginx `:443 ssl` + redirect + HSTS + WSS + sửa `add_header`, hoàn thiện staging Compose full-stack & sinh cert SAN (tách `ca.key`), đồng bộ K8s PostgreSQL `hba_file`/`fsGroup: 70` & sửa config compose local.
4. **Phase 3 — Sensitive Data Protection (`SD-03` — P1 HIGH):** Mã hóa AES-256-GCM cho `organization_alert_settings`, chuyển `approvals.approval_token` sang multi-approver `token_hash` (`jti` + SHA-256), loại bỏ plaintext legacy 2FA fallback có kiểm soát, khóa `NOT NULL` cột tenant nếu PO duyệt (`AUD-A01`).
5. **Phase 4 — Backup, Restore & Disaster Recovery (`SD-04` — P1 HIGH):** Chuẩn hóa `backup-postgres.sh` & `restore-postgres.sh`, kiểm chứng trên môi trường Linux/container thực tế, đồng bộ off-host storage, lập DR Runbook & lịch cron/monitoring.
6. **Phase 5 — Authentication & API Protection (`SD-05` — P1 HIGH):** Chuyển `rateLimit.middleware.ts` sang Redis + cấu hình `trust proxy`, hoàn thiện SMTP & Frontend tích hợp thật cho `ForgotPassword`/`ResetPassword`, rà soát chính sách Redis down cho `/auth/logout` & fail-closed Prod.
7. **Phase 6 — OWASP Application Security (`SD-06` — P0/P1 HIGH):** Vá XSS (`renderResponsePage`, 4 mẫu `EmailService`), bổ sung CSP, vá SSRF (`slack_webhook_url`, `installer.py`), vá các lỗ hổng Access Control (`AlertRuleService`, `NodeController`, `PodController`, `HealingActionService.createPolicy`, `node.routes.ts`, `GET /alert-settings` cho `VIEWER`, `recordMyActivity`), bỏ fallback `localStorage` & query `?token=`, đổi HITL 1-click sang confirmation `POST`.
8. **Phase 7 — Full Regression & Staging Verification (`SD-07` — P0/P1):** Sửa teardown `sprintASecurity.test.ts`, chạy full suite Backend / Frontend / AI Docker / Agent / Installer, chạy Staging Full-Stack HTTPS+WSS+PG-TLS E2E (`Auth → Org → Env → Cluster → Healing → HITL → Agent → Recovery Verification`), xuất trọn bộ báo cáo Sprint D.

## 4. Danh sách Các Quyết định Cần Product Owner Phê duyệt (Trước khi vào MODE 2)

Product Owner vui lòng xác nhận **6 quyết định** sau trước khi bắt đầu sửa mã nguồn ở `MODE 2`:

1. **PO Decision #1 — Phạm vi siết `NOT NULL` ở `SD-01-05` (`AUD-A01`):**
   - Duyệt cho phép tạo migration siết `NOT NULL` cho các cột `organization_id`/`environment_id` ở các bảng nghiệp vụ (`incidents`, `agent_metrics`, `node_metrics`, `agents`, `healing_policies`, `alert_event_history`, `notifications`) và giữ `cluster_id varchar` tương thích hiện tại hay yêu cầu chuẩn hóa FK UUID luôn trong Sprint D?
2. **PO Decision #2 — Edge Domain, TLS Certificate Provider & K8s Manifests (`SD-02`):**
   - Production VPS (`demo.giahungtrieu.net`) sẽ dùng **Let's Encrypt / Certbot** mount vào `nginx-proxy` hay reverse proxy/Cloudflare phía trước? Có duyệt chuyển `k8s/backend.yaml` từ `NodePort 30500` sang `ClusterIP` + Ingress HTTPS và bổ sung Redis Deployment vào `k8s/` không?
3. **PO Decision #3 — HITL 1-Click Approval UX & Token Hashing (`SD-03-02` & `SD-06-03`):**
   - Đổi link trong email từ **auto-approve trên `GET`** sang **trang xác nhận HTML + nút bấm `POST`** (an toàn chống email link-scanner tự phê duyệt lệnh K8s nguy hiểm) — Product Owner có chấp thuận thay đổi UX từ "1-click trực tiếp trên GET" sang "Click link email → Xác nhận nút Confirm (POST)" không?
   - Các phiếu HITL `PENDING` cũ trước khi deploy bản hash: chấp thuận **vô hiệu hóa buộc kỹ sư duyệt qua Dashboard** hay viết script cấp lại?
4. **PO Decision #4 — Bỏ Legacy Fallback (`localStorage` & `?token=` query string) (`SD-06-03`):**
   - Xác nhận gỡ bỏ hoàn toàn fallback đọc token từ `localStorage`/`sessionStorage` trên 6 file Frontend và bỏ `?token=` trên `/logs/stream` & `telemetryWebSocket` (SSE/WS sẽ chỉ dùng header/`ws-ticket`)?
5. **PO Decision #5 — Chính sách Redis Unavailable & RPO/RTO Mục tiêu (`SD-04-02`, `SD-05-01`, `SD-05-03`):**
   - Khi Redis sự cố ở **Production**, Rate Limiter chọn phương án **A (Fail-Closed trả `503` cho các endpoint nhạy cảm `/login`, `/refresh`, `/forgot-password`)** hay **B (Fallback sang per-process limiter ngưỡng chặt hơn 50% + bắn alert CRITICAL)**?
   - Chốt mục tiêu **RPO** (ví dụ `<= 24h` nếu backup hằng ngày hoặc `<= 1h` nếu cron định kỳ) & **RTO** (ví dụ `<= 30 phút`) cùng đích lưu trữ **off-host backup** (S3/MinIO hay VPS phụ).
6. **PO Decision #6 — Đồng bộ Legacy Test Suites & Kế hoạch Cutover `captone_db` (`SD-07-01`):**
   - Phê duyệt cập nhật các test cũ không còn phù hợp nguyên tắc bảo mật (`SB01-01`, `SB03-01b`, `WS-10`, `Agent` `'SUCCEEDED'`, `11` Frontend UI suites) sau khi hoàn tất bảo mật, và giữ nguyên tắc **chỉ chạy `--baseline` / migration trên DB test/staging** trong Sprint D (chưa chạm `captone-*` cho tới khi có cửa sổ bảo trì riêng).
